# 科研示例：先看见具体矛盾，再把它界定为问题

以下三例根据用户提供的《MoE 与 Speculative Decoding 的三个推理方向及第一性贡献》（2026-10-24）改写。原材料明确均为研究方案，尚无实验结论。案例里的成因是方案依赖的机制判断，不是已经实测确认的根因。第二、三例的流程性展开属于教学补充。

每例先讲完整的“问题—成因—洞见—方法”，让读者理解研究从哪里来，再说明本阶段停在哪里。看到后续方案，不代表发现问题时必须自动设计方法。阶段分工不等于把一个例子的因果链拆散。

## 示例一：跨请求协同提议——每个请求的好草稿，为什么未必组成一个好批次

**具体问题。** 两个代码请求各自有几种合理续写。独立生成草稿时，它们可能分别引入不同冷专家；随后系统即使把请求放进同一批，仍需为已经形成的两套需求加载专家。每个请求单看都合理，整个批次却可能付出更多搬运。

**候选成因。** 提议按请求独立选择，成本却包含共享项：多个候选用同一专家时，可能共同摊薄装载或权重访问。逐请求追求接近 target，并未显式利用这个共享机会。这个判断不等于任何专家重合都能加速，实际容量和重载同样影响成本。

**洞见。** 投机草稿是随后要被校正的提议，并非必须输出的答案。如果存在多种仍有接受价值的提议，能否在正式采样前就协调需求，让它们更容易共同执行？

**后续方法示意。** 在固定提议预算内，先用有限 lookahead 估计可能续写及专家需求，规划一个共同工作集；然后显式改变各请求的 drafter 分布，使与计划相容的续写更容易出现。按实际新分布采样，再用完整 target 验证与相应校正。共同计划可以包含值得一起加载的冷专家，不只是偏向现有缓存。

**本阶段要形成的问题。** 在固定模型和资源下，跨请求协同设计提议，能否创造独立提议与强后筛选未能覆盖的有效共享需求，并抵消规划开销和接受损失？

**为什么是 MoE × SD。** MoE 提供内容相关的共享专家成本；SD 提供可改变而后校正的提议自由度。交叉点是利用后者塑造前者，而非简单增加 batch。

**本阶段交付。** 明确部署为专家卸载还是全驻留、固定 target 语义和总提议预算；查独立资源感知提议、候选后筛选与批量共享近邻。尚不认定有足够提议自由度。若低温任务几乎只有一条可接受路径，或独立倾斜已达到同一前沿，该问题的必要性下降。

**可学习的动作。** 找出“优化按什么对象进行”和“成本按什么对象发生”之间的不一致，由此提出新问题。

## 示例二：接受路径感知驻留——验证真的用过，为什么不一定值得留到下一轮

**具体问题。** 一轮草稿给出四个位置，系统执行了这些位置的 target 验证；结果只接受第一个，后面位置走的是没有成为最终前缀的路径。这些验证期间访问的专家，如果都按普通近期访问提升驻留优先级，可能挤掉后续更有用的专家。

**候选成因。** 缓存历史将两种证据混在一起：专家为本轮计算被真实消费过，不等于这次访问同样能预测已确认前缀之后的复用。被拒候选的访问是真计算，但其对应路径没有继续保留。接受与否也不决定专家未来必然有用或无用，只可能提供额外预测信息。

**洞见。** 接受结果不仅决定哪些 token 提交，还可能帮助解释哪些访问更能代表接下来的需求。

**后续方法示意。** 所有合法候选仍完成必要验证；本轮专家访问先进入暂存或低准入状态。知道接受结果后，区分接受路径、验证专属访问与拒绝边界相关计算，分别更新跨轮驻留价值。暂存与主驻留可以是元数据策略，不要求复制两套权重。

**本阶段要形成的问题。** 在相同缓存预算下，真实接受结果是否提供超出热度、近期访问和既有复用预测的额外信息，使投机扩张不再同等冲刷未来工作集？

**本阶段交付。** 定义“路径访问”按 token/layer 还是聚合频次记录，明确更新时机和缓存对象；查强缓存及接受感知近邻。不能直接断言被拒分支访问都是污染。若两类专家复用相同、热点高度重合或现有策略已充分区分，就没有证据支持新策略。

**可学习的动作。** 同一计数背后可能包含语义不同的事件，先判断它们是否应当作为同一种决策证据。

## 示例三：可逐步提交的精确验证流——为什么早点提交常被迫缩短窗口

**具体问题。** 一个实现把多个位置并行验证成一个窗口，等整个窗口完成后才交付已接受 token。缩短窗口可以减少等待，却可能减少专家合批与权重复用；保留大窗口又可能让前面已经能确认的位置等后面。

**候选成因。** 如果当前实现把候选窗口、执行批量和输出提交绑定为同一边界，就可能引入超出模型真实依赖的等待。问题不能预设所有引擎都有这个屏障，要检查当前基线。

**洞见。** 同一专家的一批计算何时执行，与一个请求前缀何时获得完整验证结果，是两个不同决定。只有真实依赖需要等待。

**后续方法示意。** 验证行按因果依赖推进，同层就绪专家任务仍可合批；当某请求前面的 target 分布与必要状态都已就绪时，按合法接受/校正规则提交前缀，不必等整个窗口结束。拒绝后的无效后继取消或清理。

**本阶段要形成的问题。** 在保持 target 语义的前提下，提交前沿是否能与专家执行批量解耦，从而更早交付、同时保留大部分合批收益？

**本阶段交付。** 明确指标是服务端可提交时间还是客户端可见间隔，检查现有增量验证和异步引擎。若所需前缀结果本来就同时完成、现有实现已及时提交或细粒度调度抵消收益，应收缩命题。

**可学习的动作。** 检查为了实现方便被合并的几个边界，是否真的由任务依赖要求保持一致。
