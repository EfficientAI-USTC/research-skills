# 科研示例：用成因解释为什么这条解决路线值得尝试

案例根据用户提供的 2026-10-24 三方向方案改写，未取得新增实验结果。以下“根因”均为待确认的候选机制。每例保留问题、成因和解法的完整关系，本阶段重点是区分解释及定位干预点，不因讲到解法就自动执行。

## 示例一：跨请求协同提议——到底是需求不共享，还是其他地方更贵

**问题。** 多个请求分别生成高质量草稿，但合批验证仍出现较多冷专家装载。直觉上想让请求提出能共享专家的候选。

**候选根因。** 草稿按请求独立优化，专家装载却由整批需求共同决定。现有候选形成后再重排，不能创造未被提出的共享组合。

**为什么会想到这个解法。** 若有多个仍有接受价值的续写，就可以在正式采样前规划共同专家需求，再调整提议分布。可改变的是辅助提议，不是用户最终答案。

**先区分三件事。**

1. **有共享机会吗？** 在有限候选与总预算下，检查不同请求的高概率替代续写能否形成更便宜的联合需求。如果只有低概率路径能共享，根因可能是任务自由度不足。
2. **共享真的省时间吗？** 记录装载、重载、缓存容量与关键路径。集合变小但执行不快，可能由计算或其他阶段主导，不能据集合重合证明收益。
3. **必须在提议前协作吗？** 用相同信息和预算比较独立提议、独立资源偏好、强后筛选与协同计划。若后筛选已找到同样组合，就没有建立新动作的额外价值。

**最有区分力的检查。** 可以先分析有限候选内的联合组合上限，但它是离线诊断，不算在线算法。然后检查真实可实现的共同计划能否在计入规划、预测和接受变化后逼近有用空间。

**向方法阶段交接。** 只有当“可接受替代存在—联合成本有差异—现有独立策略未利用”这条链得到支持，才发展协同提议。若主要慢在 target 必须产生的昂贵答案，这个方案不能通过永久绕开这些答案解决。

## 示例二：接受路径感知驻留——执行过的访问是否混入了不同预测价值

**问题。** 候选窗口扩大后，本轮装入更多专家，下一轮却反复重载先前常用专家。想区分验证所需消费与跨轮值得保留的访问。

**候选根因。** 缓存把接受路径和被拒分支产生的访问同等记作未来热度证据，导致准入或替换偏差。

**为什么会想到这个解法。** 接受结果告诉系统哪条前缀真正继续；可以保留完整验证计算，同时重新解释已经发生的访问，用于更新下一轮驻留价值。

**诊断怎么做。** 将每次专家访问关联到层、候选位置、接受结果、缓存准入和后续复用距离。专家可能同时被接受与拒绝路径使用，因此按访问归属或分项计数，不能粗暴贴成二选一标签。拒绝位置的 target 计算还可能用于校正 token，需单列而非一律当废访问。

主要竞争解释有：总缓存容量本就不足；访问阶段性变化；被拒路径仍与后续需求高度相关；替换或预取实现故障。若是这些原因，接受标签未必能提供有用信息。

**关键对照。** 在尽可能可比的热度、近期性和专家大小条件下，检查接受标签是否仍有额外未来复用信息。固定访问 trace 的缓存回放可诊断准入价值，但真实执行会改变时间与并发，最后仍需在线验证。比较强热度、近期访问、暂存/扫描抗性等适用基线，不只比较简单 LRU。

**向方法阶段交接。** 若接受标签有稳定增量价值，再做延迟晋升或分级准入；若其作用可由普通暂存策略解释，就不把收益归因于 SD 特有反馈。被拒专家也允许晋升，接受专家也不保证保留，规则服务于预测价值而非道德式分类。

## 示例三：精确验证流——等待来自模型依赖，还是运行时屏障

**问题。** 大验证窗口中，部分 token 似乎可以更早确认，却直到窗口结束才输出。缩短窗口可能损失 MoE 专家合批效率。

**候选根因。** 运行时把三种边界绑定：一次提出多少候选、一次组织多少专家工作、一次提交多少输出。模型真实依赖不一定要求它们相同。

**为什么会想到这个解法。** 若前缀的全部必要结果已完成，后继仍在执行本身不应阻止前缀提交。因此可考虑依赖驱动验证与独立提交前沿。

**先看什么记录。** 对每个候选位置记录完整 target 分布就绪时间、接受/校正可决定时间、KV 可提交时间、服务端提交和客户端可见时间。中间层输出或部分专家完成不等于验证完成。

**竞争解释。** 若前缀 target 结果本就很晚才可得，等待是真依赖；若早已可得却未交付，才可能是窗口屏障；若服务端已交付而客户端晚显示，则是输出缓冲问题。GPU 大 kernel 不可抢占，也可能让理论上的前沿无法实际提前。

**关键检查。** 先确定可提前量，再测解除屏障的开销。以强增量验证/异步引擎为参照，在相同候选和资源下区分合批变化、kernel 数、队列开销、每轮推进和交付间隔。不能只画依赖图就宣称获得加速。

**向方法阶段交接。** 只有确有人工等待且可用合理开销解除时，发展验证流。如果提前提交必须拆碎 GEMM、显著拉长整轮，就需要继续研究批量与提交如何协调，而非宣布已同时解决两项目标。
