# 科研示例：问题、根因、洞见和具体做法要在同一例子里闭合

三个方向依据用户提供的《MoE 与 Speculative Decoding 的三个推理方向及第一性贡献》（2026-10-24）改写。它们都是待验证方案，不是已发表成果或实测结论。第一例依据已贴出的算法展开；第二、三例只提供概要，以下运行流程是教学补充，不冒充原作者完整算法。

阅读时先抓住每例的动作：改变候选如何产生、改变专家如何留下、改变验证如何推进。技术细节用于解释动作，不用术语替代动作。

## 示例一：跨请求协同提议——在候选产生前创造共享需求

**问题是什么。** 两个请求各自提出不错的续写，但分别需要两套冷专家。系统等候选产生后才合批，只能安排已有需求，未必能找到共享更好的候选组合。

**候选根因是什么。** 提议逐请求优化，验证成本却包含共享装载与容量约束。独立好的提议，不一定组成联合好的执行需求。

**洞见是什么。** SD 的最终输出由 target 验证和校正约束，草稿 q 本身有设计自由。可以让系统偏好更易共同执行的提议，再用正确校正保持最终 target 语义。

**怎么解决。**

1. 固定一小组请求、冻结 drafter、target、候选窗口和总预算；先选专家卸载场景，成本看真实权重搬运，不混用 EP 激活字节。
2. 用有限 lookahead 得到每个请求若干可能续写的基础概率和预测专家需求，计入全部扩展与预测成本。
3. 正式采样前选择共同工作集 R，权衡续写概率偏离与整组装载成本。R 可以包含多请求值得一起加载的冷专家。用于规划的候选只决定 R，不直接作为挑中的输出。
4. 固定 R 后，显式构造新提议：对基础概率 q0(v) 乘以 exp(-λ d(v;R))，再在实际支持集上归一化。d 是预测的不相容成本；有限 top-L 之外使用明确默认值，不能免费知道全词表真实路由。
5. 各请求使用独立正式随机数从新分布生成候选，完整执行 target，并按实际变换后的 q 验证与校正。后续步按各自当前前缀计算条件概率，不沿用旧 q。

**一个小例子。** 请求 A、B 都有两种合理续写。独立抽样可能选出分别需要专家组 X、Y 的组合；共同计划偏向某个能覆盖两者合理续写的 R，使共享组合更容易被提出。它提高的是提议出现的概率，不规定最终答案，更不保证昂贵专家永远不会执行。

**新增能力。** 从候选形成后安排资源，推进到候选形成前塑造需求。不是仅把请求重排，也不是看完样本挑一个再套旧提议概率。

**决定性验证。** 同样信息、草稿预算、设备和缓存下，比较独立提议、独立资源倾斜、强后筛选与协同计划，计入规划、预测、重载和接受损失。若独立倾斜达到同一前沿，或规划代价吞掉共享收益，这条贡献未建立。

**成立条件。** 新 q 的概率必须可计算；共同随机计划 R 也须纳入条件化正确性论证，不能仅凭每请求独立随机数就宣称联合精确。保持完整 target 计算与状态处理；这里不提供任意树选择的精确性证明。

## 示例二：接受路径感知驻留——本轮必须算，不等于下轮必须留

**问题是什么。** 四位置草稿只有第一个位置被接受。四个位置的必要 target 专家都算过、装过，如果一律按访问更新缓存，未延续分支可能冲掉后续更有用的专家。

**候选根因是什么。** 本轮访问计数混合了计算消费和未来复用证据。接受结果可能帮助区分二者，但尚未证明有增量预测价值。

**洞见是什么。** 保持本轮精确验证，把接受结果用于跨轮驻留，而非用它事后省略本轮本应完成的计算。

**怎么解决：示意实现。**

1. 每个验证轮记录专家访问的层、候选归属与当前驻留信息；共享专家允许同时有多类访问计数。
2. 新访问先暂存或低优先级准入。暂存可以只是逻辑状态，不要求复制权重，也不能把所有本轮专家无限塞进显存；容量不足仍按声明的规则执行和补取。
3. 接受结果出来后，对延续路径提供较强复用证据，对验证专属访问采用较低或独立的准入证据；拒绝边界及校正相关访问单列处理。
4. 与热度、近期性、复用距离和搬运代价一起更新保留决策。被拒路径专家若反复复用，仍可晋升；接受路径专家也可在证据不足时淘汰。

**一个小例子。** 本轮早期接受位置反复用 A、B，后继被拒分支临时引入 C、D、E。普通访问计数可能让后来的 C、D、E 挤掉 A、B；新策略等待接受反馈后再判断是否晋升。例子只说明动作，不能假定 A、B 下一轮必然更有用。

**新增能力。** 给历史访问增加接受语义，区分短期消费与跨轮预测；不是把被拒候选当作没计算过，也不是简单丢掉所有被拒专家。

**决定性验证。** 先检验接受标签在匹配热度等条件后是否仍有预测价值，再与强准入、暂存、复用预测基线比较重载及端到端时间。若普通扫描抗性策略即可解释全部收益，应撤回 SD 特定机制主张。

## 示例三：可逐步提交的精确验证流——执行能合批，提交不必整窗等待

**问题是什么。** 大窗口有利于同专家合批；整窗结束才交付又让早期 token 等后继。简单缩短窗口可能改善交付，却损失执行效率。

**候选根因是什么。** 运行时将候选窗口、专家计算批量和提交粒度绑定为一个边界。某些等待来自实现屏障，而非模型真实依赖。

**洞见是什么。** 谁能先提交由完整前缀验证决定；哪些工作一起执行由同层专家就绪与批量效率决定。两个边界可以分别管理。

**怎么解决：示意实现。**

1. 将候选位置表示为带因果依赖的验证行，记录 attention、专家计算、输出分布及 KV 的就绪状态，不跳过合法候选所需的 target 计算。
2. 同层就绪专家任务进入有界队列，达到合适批量或等待阈值时执行；不能为凑大批而无限拖延最早可确认位置。
3. 维护每请求的提交前沿：只有此前位置均已确认、当前完整 target 分布与必要状态已就绪，才按既定接受/校正规则推进输出。部分层或部分专家完成不能提交。
4. 拒绝后清理无效后继及临时 KV，保留已提交状态；实际 GPU kernel 可能无法即时取消，已执行浪费照实计费。正确性相对固定逐请求 target 语义单独论证。

**一个小例子。** 窗口有六个位置。如果前两个的完整验证与状态已经就绪，而后面仍有任务，系统可以交付已确认前缀；其他请求同层就绪工作仍可合批。如果大 kernel 让六个位置只能同时完成，这个例子没有可兑现提前量，不能凭逻辑图创造速度。

**新增能力。** 让输出提交跟随合法前沿推进，同时尽量保留专家执行的批量效率。核心是运行时接口与执行组织，不是多加一个输出线程。

**决定性验证。** 比较大窗口整窗提交、小窗口、强增量/异步基线和新运行时，报告实际可见间隔、总时间、kernel 开销、批量效率与必要的请求级指标。若改善只来自更小批量，或队列开销抵消收益，“不以牺牲批量换交付”的主张没有建立。
